# GL-07: Luna insertion prompts and output limits

Session date: 2026-09-16 America/New_York; capture timestamps use UTC. Development model: Astra High. Runtime model: `gpt-5.6-luna` at `https://api.openai.com/v1/responses`.

## Decision

Retain the production prompt P0 and fixed 96-token output limit. Compact prompts reduced request latency substantially in this screen, but none passed the predeclared quality criterion; conditional caps also showed no supported benefit. This is an inconclusive quality comparison, not proof that P0 is optimal or that the alternatives are worse. No prompt finalist was promoted, and the 56-case holdout remains unused for live inference.

The prerequisite boundary repair **is implemented**: wait for protocol completion and preserve required nested closers. This repair is supported by deterministic regressions, separately from the prompt experiment. Production remains Luna, reasoning `none`, atomic ghost-text display, and the existing insertion-only workflow.

GL-07 is complete as an evaluated, no-promotion result. ## Review and limitations

The restarted screen produced 268 unmatched, nonempty completion responses. Separate representation checks recognized another 3/3/4/6 responses for P0/P1/P2/P3 using Go formatting, Python AST equality, or emitted TypeScript JavaScript. The TypeScript check does not establish type correctness. A further [static review](2026-09-16-gl07-manual-review.json) recognized 5/5/5/7 responses, including equivalent copy loops, formatting and unconstrained error wording. These 22 decisions identify exact captured programs by hash. They are one assistant's review, not independently adjudicated behavioral tests.

The resulting recognized-reference-equivalence lower bounds are 41/39/39/38 of 102. They do not replace the frozen primary scores, establish a winner, or classify the remaining responses as incorrect. The review exposed both real failures and evaluation ambiguity:

- Partial-token continuation is unreliable: Python `sor` became `sort(xs)` rather than `sorted(xs)`, and `enum` became `enumrate(xs)` in some responses. A missing space after `await` can merge two identifiers.
- Existing quotes, brackets and slice delimiters are sometimes echoed, leaving malformed source. Other candidates parse but call an undefined name or use a function value where a call is needed.
- Some Go suggestions reverse `copy` arguments, use the wrong division guard or send a channel into itself. Syntax alone misses these errors.
- Authored unknown-dependency abstention was rarely honored. Its labels express a conservative policy; they are not proof that every conceivable suggestion is inappropriate.
- Some intended answers are not inferable from visible context. For example, both an empty-string fallback and `"anonymous"` can be reasonable; arbitrary JSON/YAML values may have many valid completions. Generic function names also hide intended behavior. Exact reconstruction overstates failure in those cases.

These findings favor a focused follow-up on observable intent, realistic cursor positions and partial-token insertion. Adding more prompt text or same-file context without isolating these failures would not establish that the underlying issue is solved. Compact P1/P2 remain useful experimental candidates, with no production promotion yet.

## Output-budget sensitivity study

The protocol froze P0 and compared B0 fixed96, B1 short48/block96 and B2 short96/block160 on 32 cases from 16 hash-selected development families, three repetitions per arm (288 requests). All completed, with no incomplete responses or transport failures. Selection used a fixed hash ordering within each language, not observed scores. Eight families are Go and two each are TypeScript, Python, YAML and JSON; both cursor states are included. No abstention family is in this subset.

The short/block request classification uses only visible current-line context, not removed answers or gold labels. Per arm, 69 requests were classified short and 27 block. B1 therefore actually used 48 tokens for 69 requests and 96 for 27; B2 used 96 for 69 and 160 for 27. No prompt-screen response reached 48 output tokens, and the largest budget-study response used only 24. The cap was nonbinding in this sample. This is a small exploratory sensitivity check, not full development confirmation.

| Policy | Raw / processed reference-data matches, /96 | Nonempty returns, /96 | Raw / processed syntax failures, /96 | Request p50 / p95 |
| --- | ---: | ---: | ---: | ---: |
| B0 fixed96 | 20 / 26 | 87 | 41 / 26 | 2,336 / 3,773 ms |
| B1 short48 / block96 | 18 / 24 | 88 | 40 / 26 | 2,383 / 3,826 ms |
| B2 short96 / block160 | 20 / 26 | 88 | 38 / 24 | 2,182 / 3,757 ms |

The paired 16-family primary-rate difference was −2.1 percentage points for B1 (descriptive 95% interval −6.3 to 0) and approximately zero for B2 (−3.1 to +3.1). No raw-valid reconstruction became syntax-invalid after processing. Supplemental representation matches added 9/9/10; exact program-hash matches to the earlier [static review](2026-09-16-gl07-budget-review.json) added another 9/9/8, giving recognized-reference-equivalence lower bounds of 44/42/44. This still leaves unverified behavior and does not establish a cap winner. All arms had processed-length p50/p95 of 7/54 characters; known-good character totals were 171/159/170. Language/category results and usage are preserved in the machine summary.

Within the requested short group, B0/B1/B2 matched 14/12/14 of 69 responses, with request p50 2,365/2,389/2,225 ms and p95 4,189/3,341/3,599 ms. Within the requested block group, all matched 12 of 27, with p50 2,255/2,382/2,131 ms and p95 3,255/5,254/3,766 ms. These small groups show timing variability without a consistent cap advantage; they do not establish an optimum block limit.

Retain B0. The larger block cap did not repair any observed truncation, and the smaller short cap did not improve measured latency. Do not interpret small timing differences as causal gains with these nonbinding limits and a 16-family subset. A useful follow-up cap test needs representative longer blocks and actual truncation pressure, after improving the quality fixtures.
